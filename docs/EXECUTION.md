# Codex 最小自动执行循环

## 执行边界

- 业务范围唯一以 docs/功能开发清单.xlsx 的一期和二期为准；三期不进入当前 Goal。
- 工作包的目标、范围、依赖、非目标、验收标准和本地验证命令只保存在 docs/work-packages/。
- docs/STATE.json 只保存当前动态状态，不重复保存工作包依赖、范围或验收标准。
- 仅执行本地测试、构建和检查命令，不依赖 GitHub Actions、远程 CI 或其他远程流水线。

## 固定阶段顺序

| 当前阶段 | 工作包顺序 | 阶段完成后的处理 |
| --- | --- | --- |
| S1 工程基础 | WP-01、WP-02、WP-03、WP-04 | 执行本地自动门禁，通过后进入 S2 |
| S2 一期 | WP-05、WP-06、WP-07、WP-08、WP-09 | 执行本地自动门禁，通过后等待一期人工阶段验收 |
| S3 二期 | WP-10、WP-11 | 执行本地自动门禁，通过后等待二期人工阶段验收 |
| S4 最终交付 | WP-12 | 执行本地自动门禁，通过后等待最终人工阶段验收 |

阶段自动门禁使用该阶段最后一个工作包定义的本地验证命令；S1 额外重新执行 WP-01 的后端、PC、H5、数据库迁移和 ArchUnit 验证。自动门禁通过后，S1 直接进入 S2；S2、S3 和 S4 先更新为等待人工阶段验收。

## 自动执行算法

1. 读取 AGENTS.md。
2. 读取 docs/GOAL.md、docs/ARCHITECTURE.md、docs/EXECUTION.md 和 docs/STATE.json。
3. 若 waiting_for_human_stage_acceptance 为 true，停止并等待用户输入“批准并继续”。
4. 若 current_work_package 非空，恢复该工作包；否则在当前阶段顺序中选择依赖已全部列入 completed_work_packages 的第一个未完成工作包。
5. 读取对应工作包规范。
6. 只实现该工作包的范围，不擅自扩大需求。
7. 执行工作包定义的本地测试、构建和检查命令。
8. 验证失败时，先在该工作包范围内分析并修复，再重复验证。
9. 验证通过后，更新 STATE.json：记录已完成工作包、清空阻塞原因，并设置同一阶段下一个可执行工作包；创建包含工作包 ID 的独立 Git 提交；随后自动继续执行下一个工作包。
10. 当前阶段全部工作包完成后，执行该阶段的本地自动门禁。
11. 自动门禁通过后，S1 直接进入下一阶段；S2、S3、S4 将 waiting_for_human_stage_acceptance 设为 true 并停止。
12. 用户输入“批准并继续”后，清空人工验收等待和阻塞原因，进入下一阶段并设置其第一个可执行工作包；最终交付获批后保持无当前工作包的完成状态。

## 停止条件

仅在以下情况停止并报告：

1. 到达一期完成、二期完成或最终交付的人工阶段验收。
2. 功能开发清单存在无法合理判断的冲突。
3. 需要真实第三方账号、凭据或外部服务。
4. 本地测试经过合理修复后仍然失败。
5. 工作包需要明显扩大范围。
6. 存在无法判断归属的用户未提交修改。
7. 发生可能破坏数据、Git 历史或现有实现的高风险操作。

普通代码问题、测试失败、格式问题和编译问题不构成立即停止条件，必须先在当前工作包范围内自主分析和修复。
