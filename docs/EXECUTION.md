# 执行规则（EXECUTION.md）

## 文档权威顺序

1. 用户当前明确指令。
2. 根目录 `AGENTS.md`。
3. `docs/GOAL.md`。
4. `docs/ARCHITECTURE.md`。
5. `docs/EXECUTION.md`（本文件）。
6. `docs/STATE.json`（动态状态唯一真源）。
7. 当前工作包规范（`docs/work-packages/WP-XX.md`）。
8. `docs/功能开发清单.xlsx`（业务范围唯一真源）。
9. `docs/reference/flows/`（流程参考）。
10. `old/`（遗留参考）。

## 新会话读取顺序

1. `AGENTS.md`
2. `docs/GOAL.md`
3. `docs/EXECUTION.md`
4. `docs/STATE.json`
5. 当前工作包

## 工作包状态

工作包状态只允许：

- `draft`：待准备。
- `ready`：依赖已满足，可以执行。
- `in_progress`：正在执行。
- `blocked`：被阻塞。
- `done`：已完成。

状态只保存在 `docs/STATE.json`，工作包 Markdown 中不得保存动态状态。

## 执行算法

1. 读取 `AGENTS.md`、`docs/GOAL.md`、`docs/EXECUTION.md`、`docs/STATE.json`。
2. 如果存在 `in_progress` 工作包，继续执行。
3. 否则选择依赖全部完成的第一个 `ready` 工作包。
4. 将其改为 `in_progress`。
5. 只完成该工作包范围。
6. 执行工作包要求的验证命令。
7. 验证通过后改为 `done`。
8. 创建包含工作包 ID 的 Git 提交。
9. 将下一个依赖已满足的工作包改为 `ready`。
10. 自动继续执行。
11. 当前阶段所有工作包变为 `done` 后，执行门禁验证命令。
12. 根据门禁类型执行转换规则（见下方"门禁转换规则"）。

## 停止条件

出现以下情况必须停止：

- 到达人工或混合阶段门禁（见"门禁转换规则"）。
- 自动门禁验证命令失败。
- Excel 需求存在无法判断的冲突。
- 测试经过合理修复后仍无法通过。
- 需要真实外部服务、账号或凭据。
- 工作包范围发生重大变化。
- 存在用户未提交修改且无法判断归属。

## 跨阶段执行约束

以下约束防止工作包在阶段门禁通过前提前执行：

1. `ready` 和 `in_progress` 工作包的 `stage` 必须等于 `STATE.stage`。
2. `draft` 工作包可以属于未来阶段。
3. `waiting_human` 门禁期间，不得存在任何 `ready` 或 `in_progress` 工作包。
4. 当前阶段门禁未通过前，下一阶段工作包不得变为 `ready`。
5. `STATE.gate` 不为 `null` 时，必须等于当前阶段对应的门禁（S0→G0、S1→G1、S2→G2、S3→G3、S4→G4）。

## 门禁转换规则

### 自动门禁（如 G1）

当前阶段所有工作包变为 `done` 后：

1. 执行该门禁定义的全部验证命令。
2. 验证全部通过后，将 `STATE.stage` 更新到下一阶段。
3. 清空 `STATE.gate` 和 `STATE.gate_status`。
4. 将下一阶段中依赖全部满足的第一个工作包改为 `ready`。
5. 自动继续执行该工作包。

验证未通过时：停止，报告失败原因，等待用户处理。

### 人工或混合门禁（如 G0、G2、G3、G4）

当前阶段所有工作包变为 `done` 后：

1. 将 `STATE.gate` 设置为当前门禁 ID。
2. 将 `STATE.gate_status` 设置为 `waiting_human`。
3. 不得将下一阶段工作包改为 `ready`。
4. 停止执行，等待用户批准。
5. 用户批准后，系统自动执行阶段转换（更新 `STATE.stage`、清空门禁、设置下一阶段首个 `ready` 工作包）。

## 阶段与门禁

### S0：需求和架构确认

**任务**：

- 读取功能开发清单。
- 确认一期、二期范围。
- 确定业务包。
- 确定数据库重新设计原则。
- 确定必要技术版本。
- 生成实际工作包。

**G0**：人工门禁。需要用户确认总 Goal、范围、业务包划分、工作包清单和关键技术选型。G0 通过后自动进入 S1。

### S1：工程骨架与平台基础

**任务**：

- 后端工程骨架。
- PC 工程骨架。
- uni-app 工程骨架。
- pnpm workspace。
- 数据库迁移基础。
- 身份、权限、组织、流程、文件、消息、审计基础。
- ArchUnit。
- CI 和基础测试。

**G1**：自动门禁。要求后端、PC、uni-app H5 构建和测试通过，数据库迁移测试通过，ArchUnit 通过，CI 通过。

### S2：一期功能

**任务**：执行 Excel 中全部一期工作包。每个工作包完成后自动执行测试、构建、更新状态、创建提交、继续下一个 ready 工作包。

**G2**：混合门禁。自动条件：一期工作包全部 done、一期需求全部覆盖、自动化测试通过、PC 与 H5 构建通过。自动条件通过后停止，等待用户进行一次阶段验收。

### S3：二期功能

**任务**：执行 Excel 中全部二期工作包。

**G3**：混合门禁。二期工作包全部完成、回归测试通过、用户进行一次阶段验收。

### S4：集成与发布

**任务**：全量集成测试、安全检查、性能基础验证、安装备份恢复、发布回滚、用户文档、运维文档。

**G4**：最终人工门禁。

## 提交规则

- 每个工作包至少一个独立提交。
- 格式：`feat(WP-XX): 描述` 或 `fix(WP-XX): 描述`。
- 提交前运行当前工作包定义的验证命令。
- 禁止使用：`1`、`add`、`update`、`done`。
- 不得修改 Git 历史。
- 不得擅自删除用户修改。
