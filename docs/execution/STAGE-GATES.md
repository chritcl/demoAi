# 阶段与门禁（STAGE-GATES）

本文件定义 demoAi 项目从 S0 到 S6 的阶段划分和每个阶段结束时的门禁条件。

当前阶段、活动门禁和门禁状态以 `docs/execution/STATE.json` 为唯一真源；本文件只定义阶段与门禁的静态规则，不记录当前状态。

## 阶段总览

| 阶段 | 名称 | 目标 | 门禁 |
|---|---|---|---|
| S0 | 仓库治理与执行底座 | 建立执行体系、文档真源、遗留隔离、凭据治理、Goal、工作包协议、状态机、门禁、验证器、基础 CI | G0 |
| S1 | 需求与架构基线 | 冻结需求、范围、领域地图、数据所有权、业务包依赖、API/安全/非功能基线、核心 ADR | G1 |
| S2 | 工程骨架 | 建立可运行、可测试的后端/PC/移动端骨架、数据库迁移基线、ArchUnit、基础 CI | G2 |
| S3 | 第一条端到端纵向切片 | 实现一个完整业务闭环（例如通知公告、请休假或信息发布），贯通数据库、后端、API、PC、uni-app H5、权限、审计、自动化测试 | G3 |
| S4 | 一期能力 | 实现一期全部需求与测试证据 | G4 |
| S5 | 二期能力 | 实现二期全部需求与测试证据 | G5 |
| S6 | 发布准备 | 安全验证、性能基线、部署、备份恢复、发布回滚、运维文档、用户验收 | G6 |

## 各阶段工作包

### S0 工作包

- WP-000：仓库审计与凭据风险处理
- WP-001：文档真源重建
- WP-002：Codex 执行协议
- WP-003：架构边界与 ADR 待办
- WP-004：执行体系自动验证
- WP-005：G0 后执行体系一致性修复

### S1 工作包

- WP-006：需求基线与阶段映射
- WP-007：领域地图与业务包边界
- WP-008：核心技术与架构 ADR
- WP-009：API、安全与非功能基线
- WP-010：G1 门禁材料汇总

### S2 及以后工作包

S2 至 S6 的工作包在 S1 门禁通过后由后续规划定义。

## 阶段约束

### S0 约束

- 只允许文档、协议、状态机、验证器、基础 CI 类工作。
- 禁止创建后端业务工程、PC 工程、uni-app 工程、数据库迁移脚本或业务代码。
- 禁止用空类、空目录或占位工程冒充架构完成。

### S1 约束

- 只允许需求基线、领域地图、数据所有权、业务包依赖方向、跨包公开契约、数据架构、API 契约、安全与非功能需求、技术版本 ADR、流程引擎 ADR、前端与移动端架构 ADR 类工作。
- 禁止创建后端业务工程、PC 工程、uni-app 工程、数据库迁移脚本或业务代码。
- 禁止用空类、空目录或占位工程冒充架构完成。

### S2 约束

- 允许创建后端、PC、移动端骨架。
- 允许创建数据库迁移基线。
- 允许引入 ArchUnit 和基础测试。
- 业务代码仍然只能为空骨架或示例，不得冒充业务完成。

### S3 约束

- 只选择一个小而完整的业务闭环，例如通知公告、请休假或信息发布。
- 必须贯通数据库、后端业务包、API、PC、uni-app H5、权限、审计、自动化测试。
- 不允许跳过端到端验证而进入 S4。

## 门禁定义

### G0：S0 结束门禁

- 类型：`hybrid`（自动条件 + 人工确认）
- 自动条件：
  - WP-000 至 WP-005 均为 `done`。
  - `node tools/execution/validate.mjs` 通过。
  - 工作区干净。
- 人工条件：
  - 用户确认 `old/` 之外没有新的真实凭据。
  - 用户确认当前文档真源和架构边界可接受。
- 通过后状态：进入 S1，`active_gate` 设为 `null`。

> 注：WP-005 完成后，G0 的自动条件已经满足。G0 已由用户提交 `docs/execution/gates/G0.md` 批准为 `approved`。

### G1：S1 结束门禁

- 类型：`human`
- 条件：
  - 需求范围批准。
  - 领域地图批准。
  - 业务包清单批准。
  - 数据所有权批准。
  - 业务包依赖方向批准。
  - 跨包调用契约批准。
  - 核心 ADR（ADR-001 至 ADR-010 中所有 S1 相关 ADR）被批准为 `accepted`。
  - 数据架构批准。
  - API、安全和非功能基线批准。
- 不要求：
  - 工程骨架已创建或运行。
  - 流程引擎实现已完成。
- 通过后状态：进入 S2，`active_gate` 设为 `null`。

### G2：S2 结束门禁

- 类型：`automatic`
- 条件：
  - 后端、PC 端、移动端骨架可构建。
  - 数据库迁移基线可执行。
  - CI 通过。
  - ArchUnit 通过。
- 通过后状态：进入 S3，`active_gate` 设为 `null`。

### G3：S3 结束门禁

- 类型：`human`
- 条件：
  - 第一条端到端业务闭环完成并通过测试。
  - 用户验收通过。
- 通过后状态：进入 S4，`active_gate` 设为 `null`。

### G4：S4 结束门禁

- 类型：`automatic`
- 条件：
  - 一期业务全部完成。
  - 集成测试通过。
  - 性能基准可接受。
- 通过后状态：进入 S5，`active_gate` 设为 `null`。

### G5：S5 结束门禁

- 类型：`automatic`
- 条件：
  - 二期业务扩展完成。
  - 回归测试通过。
- 通过后状态：进入 S6，`active_gate` 设为 `null`。

### G6：S6 结束门禁

- 类型：`human`
- 条件：
  - 系统验收通过。
  - 部署文档完整。
  - 用户签署交付。
- 通过后状态：项目完成。

## 门禁状态机

每个门禁具有以下状态：

- `pending`：未开始评估。
- `in_review`：正在评估条件。
- `automatic_passed`：自动条件通过，等待人工确认（仅 hybrid 门禁）。
- `waiting_human`：到达人工条件，等待用户批准。
- `approved`：已批准，可进入下一阶段。
- `rejected`：未通过，需修复后重新评估。

## 自动连续执行

- `STATE.json` 中的 `auto_continue_until_gate` 为 `true` 时，Codex 可自动连续执行处于 `ready` 的工作包，直到遇到人工门禁或强制停止条件。
- 当遇到 `waiting_human` 状态时，必须停止并等待用户明确批准。

## 阶段升级流程

1. 本阶段所有工作包完成并提交。
2. 运行阶段验证命令。
3. 评估门禁条件。
4. 如果是自动门禁，通过则进入下一阶段，并更新 `active_stage` 和 `active_gate`。
5. 如果是人工门禁，状态设为 `waiting_human` 并等待用户批准。
6. 用户批准后，更新 `STATE.json` 中的 `active_stage` 和 `active_gate`。

## 与执行协议的关系

`EXECUTION-PROTOCOL.md` 定义工作包执行流程；`STAGE-GATES.md` 定义阶段和门禁条件。两者共同构成完整的执行控制体系。当前状态以 `STATE.json` 为唯一真源。
