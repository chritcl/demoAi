# WP-005：G0 后执行体系一致性修复

## 目标

修复仓库中已经出现的动态状态漂移、阶段模型冲突、需求追踪错误、业务包编号错位、验证器覆盖不足等问题，确保执行体系在 G0 通过后仍保持一致性和可继续执行性。

## 范围

- 修复动态状态真源，删除 README.md、AGENTS.md 等文档中的硬编码状态。
- 恢复 S0～S6 阶段模型，调整 G1/G2 门禁条件。
- 建立 S1 的 WP-006～WP-010 工作包。
- 修复需求追踪矩阵的阶段统计和业务包映射。
- 修复领域地图中的 owner 冲突和不确定表述。
- 修复数据架构中的未经确认判断。
- 修正 ADR-001 的事实描述，状态保持 proposed。
- 修复旧 application.yml 中 Redis 密码环境变量错误。
- 补充 G0 门禁证据。
- 扩展执行验证器，覆盖状态漂移、相对链接、业务包一致性、需求阶段统计、owner 检查、门禁证据、循环依赖等。
- 修复 GitHub Actions 空白检查逻辑。
- 同步 docs/README.md 导航。

## 不在范围

- 不开始 ADR 技术方案决策。
- 不创建后端、PC、uni-app 工程骨架。
- 不创建数据库迁移脚本。
- 不实现业务 Controller、Service、Mapper、Entity 或页面。
- 不开发一期、二期、三期业务功能。
- 不推送远程。
- 不修改 Git 历史。
- 不拆分或合并业务包。
- 不决定流程引擎或最终技术版本。

## 最小 Bootstrap 例外说明

由于当前 STATE.json 在 G0 通过后进入 S1，但尚未创建任何 S1 工作包，也没有处于 in_progress 的工作包，因此允许一次最小 Bootstrap：创建本规范并将 WP-005 直接设为 in_progress。该例外是因为没有可归属的已存在工作包，且修复执行体系一致性本身是继续执行的前提。本 Bootstrap 只执行一次，WP-005 全部完成后统一提交。

## 风险

- 高：动态状态已在多个文档中硬编码，容易再次漂移。
- 高：功能清单的“阶段”列与“难易度统计”页口径不一致，需人工确认。
- 中：业务包编号仍为候选基线，需 G1 批准。
- 中：旧 Git 历史保留凭据，G0 只能证明当前树已脱敏，不能证明外部凭据已轮换。

## 验收标准

1. `STATE.json` 是唯一的动态状态真源。
2. 阶段模型恢复为 S0～S6。
3. S1 至少存在一个可继续执行的 ready 工作包（WP-006）。
4. 需求追踪矩阵与功能清单、系统导图一致，阶段统计为 31/14/8。
5. 业务包编码在 active 文档中保持一致，不存在 s4_office 等错误编码。
6. 公文交换保持三期 deferred，不进入当前实施范围。
7. 验证器 0 错误，新增规则能够发现本次已出现的状态漂移和业务包错位。
8. CI 能够真实检查提交或 PR 引入的空白错误。
9. 不修改旧 Git 历史，不推送远程。
